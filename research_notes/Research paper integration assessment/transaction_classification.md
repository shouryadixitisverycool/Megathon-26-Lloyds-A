# Transaction-classification paper integration assessment

Scope: compare the two assigned papers with the repository’s transaction categoriser, training inputs, taxonomy/feature contracts, uncertainty behavior, tests, and reports. This is a static audit; proposed work below is not implemented.

## 1. Hierarchical Financial Transaction Classification

### Takeaway

**Overall status: Partial only at the broad-task level; the paper’s defining hierarchical method is not implemented.** GreenPath classifies merchant descriptions and has deterministic category rules, but emits one flat category. It has neither the paper’s two-input, two-head model nor a parent/child taxonomy and hierarchy-aware child correction. [Classifier](../../src/greenpath/models/transaction_classifier.py#L1-L40) · [category enum](../../src/greenpath/contracts/enums.py#L34-L43)

### Identity and method

The paper is Antonio J. G. Busson et al., “Hierarchical Classification of Financial Transactions Through Context-Fusion of Transformer-based Embeddings and Taxonomy-aware Attention Layer,” arXiv:2312.07730 (submitted 12 Dec 2023; related proceedings DOI 10.5753/bwaif.2023.229322). The primary-source record and full text are [arXiv](https://arxiv.org/abs/2312.07730) and [arXiv HTML](https://arxiv.org/html/2312.07730v1); the supplied extraction is [here](../../research-papers/hierarchical-financial-transaction-classification.md#L1-L25).

Two-headed DragoNet separately encodes merchant name and business-activity text with Transformer encoders, fuses the representations, and predicts macro and micro categories with two heads. At inference, its Taxonomy-aware Attention Layer masks micro-category predictions incompatible with the selected macro category. The paper describes 15 macro and 82 micro categories and volunteer annotations on BTG Pactual card/account data; it reports macro/micro F1 of 93.02/84.54 on card transactions and 95.07/86.66 on account transactions. Its reported experiment uses a 10-fold split; the described protocol does not establish a merchant-disjoint holdout. These private-data results are not directly comparable to GreenPath’s synthetic merchant-heldout results. [Method and taxonomy](../../research-papers/hierarchical-financial-transaction-classification.md#L111-L129) · [dual-head and hierarchy correction](../../research-papers/hierarchical-financial-transaction-classification.md#L192-L218) · [TAL](../../research-papers/hierarchical-financial-transaction-classification.md#L266-L325) · [reported split and metrics](../../research-papers/hierarchical-financial-transaction-classification.md#L340-L355) · [results](../../research-papers/hierarchical-financial-transaction-classification.md#L477-L517) · [primary source](https://arxiv.org/html/2312.07730v1)

The current output contract gives each input exactly one category; `category_confidence` is the top predicted logistic-regression probability, while a rule hit receives confidence 1.0. Empty normalized text becomes `OTHER` with confidence 0.0. There is no macro/micro output or uncertainty threshold in this classifier, so an `OTHER` fallback should not be mistaken for hierarchy or principled abstention. ### Concrete staged integration plan

1. **Taxonomy contract first (small-to-medium; domain-owner dependency).** Agree a use-case taxonomy and versioned parent mapping before changing model code: the eight current labels do not themselves identify suitable parents. Add a taxonomy definition/validator alongside the transaction contracts, requiring every modeled leaf to have an allowed parent and rejecting invalid mappings (and cycles if a general DAG is supported). Keep the existing `category` output and spend features unchanged until a reviewed mapping exists. The shared contracts are explicitly canonical/frozen, and the feature registry is versioned, so coordinate any public/internal contract or feature-version change with its owner. [Contract ownership/version](../../CONTRACTS.md#L1-L8) · [feature version](../../src/greenpath/pipelines/feature_registry.py#L14-L25) · [feature version constant](../../src/greenpath/config.py#L21-L26)
2. **Add data only when genuinely available (medium; data dependency).** If a real upstream merchant activity descriptor exists, extend the approved input schema and training/inference transform together. Do not synthesize an activity field from `true_category`, as that would encode the answer in the feature. Without that field, a two-head, hierarchy-constrained model can still be tested on one description, but must be reported as an adaptation—not a reproduction of the paper’s context fusion. [Current transaction inputs](../../src/greenpath/pipelines/schemas.py#L72-L93) · [synthetic truth construction](../../src/greenpath/data_generation/generator.py#L740-L760)
3. **Train a side-by-side challenger (large for faithful DragoNet; compute/dependency dependency).** Add a separate hierarchical classifier rather than silently replacing the stable single-label model. Train macro and micro heads on the same merchant-disjoint fit set; after selecting the macro class, mask child scores to its valid descendants. Preserve the legacy category for Customer 360 until the challenger is accepted. The exact Transformer implementation would add a deep-learning dependency and inference-cost question absent from the current scikit-learn stack. [Existing classifier dependency](../../pyproject.toml#L10-L27) · [pipeline’s categorise/train boundary](../../src/greenpath/pipelines/run.py#L125-L131) · [Customer 360 consumes category](../../src/greenpath/pipelines/customer360.py#L317-L356)
4. **Acceptance checks before any submission claim.** Add tests that every leaf has a valid parent, every emitted parent/child pair is compatible (zero violations after correction), and legacy output/Customer 360 remain stable. On the *same* merchant-heldout set, report macro F1, micro F1, per-leaf support/F1, and raw-versus-corrected hierarchy violations against the flat baseline; mark unsupported leaves rather than hiding them. A proposed go/no-go is no material decline at either level and a pre-registered improvement on the chosen task (e.g. ≥0.03 absolute macro F1 with a positive bootstrap confidence interval); this is a suggested project criterion, not a result claimed by the paper.

**Submission payoff:** a validated hierarchy can make category rollups coherent and explicitly test impossible parent/child combinations, which is useful where category spend feeds downstream customer features. Its payoff is conditional: GreenPath first needs an agreed domain taxonomy, suitable leaf labels, and evidence on unseen merchants; merely adding two output columns or calling rules “attention” would not demonstrate the paper’s contribution. [Category spend feature contract](../../src/greenpath/pipelines/feature_registry.py#L22-L55) · [downstream category aggregation](../../src/greenpath/pipelines/customer360.py#L91-L140)

## 2. Scalable and Weakly Supervised Bank Transaction Classification

### Takeaway

**Overall status: Not implemented for the defining weak-supervision method; partial overlap in text rules, a supervised classifier, and merchant-heldout evaluation.** GreenPath’s hand-written rules are an inference-time first stage. They do not produce a matrix of weak labeling-function outputs, an abstention-aware probabilistic label model, or training targets for a discriminative model. [GreenPath rules/model](../../src/greenpath/models/transaction_classifier.py#L1-L40) · [paper’s weak-label pipeline](../../research-papers/weakly-supervised-bank-transaction-classification.md#L268-L349)

### Identity and method

The paper is Liam Toran, Cory Van Der Walt, Alan Sammarone, and Alex Keller (Flowcast.ai), “Scalable and Weakly Supervised Bank Transaction Classification,” arXiv:2305.18430v2 (submitted 28 May 2023; revised 10 June 2023). Primary-source record and full text: [arXiv](https://arxiv.org/abs/2305.18430) · [arXiv HTML v2](https://arxiv.org/html/2305.18430v2); supplied extraction: [local copy](../../research-papers/weakly-supervised-bank-transaction-classification.md#L1-L17).

Its defining sequence is transaction preprocessing/grouping, independent labeling functions (LFs) over text and spending patterns, an aggregation/label model that creates probabilistic weak labels, then a discriminative model. Text LFs include embedding-based anchors; the reported downstream model combines FastText transaction text with amount/date sequences in GRUs. The authors frame tasks as separate binary classifiers. They describe a small (500 or fewer) annotated set for calibration/evaluation, report an average 0.91 balanced accuracy across nine tasks, and note the small/biased evaluation labels and that precision is not representative of population prevalence. These binary-task results are not comparable to GreenPath’s flat multiclass macro F1. [Data/annotation scope](../../research-papers/weakly-supervised-bank-transaction-classification.md#L95-L133) · [LFs and anchors](../../research-papers/weakly-supervised-bank-transaction-classification.md#L285-L332) · [label model](../../research-papers/weakly-supervised-bank-transaction-classification.md#L333-L349) · [GRU model](../../research-papers/weakly-supervised-bank-transaction-classification.md#L350-L389) · [reported results and caveats](../../research-papers/weakly-supervised-bank-transaction-classification.md#L560-L621) · [precision/prevalence limitation](../../research-papers/weakly-supervised-bank-transaction-classification.md#L899-L945) · [primary source](https://arxiv.org/html/2305.18430v2)

**Fallback and abstention are different here.** An unmatched GreenPath rule means “send this row to the supervised classifier”; it is not an LF abstention that contributes evidence to a label model. The classifier still emits the top category for every non-empty text, and the tests assert exactly one valid category per row. Empty text is assigned `OTHER`/0.0; there is no configurable low-confidence abstain or review result. The paper’s LF abstentions concern label-generation coverage, not a guaranteed final abstention policy; it also says its Snorkel-based label model did not incorporate abstentions in posterior probabilities, a limitation to re-check rather than copy. ### Evaluation evidence and concrete staged plan

The existing evaluation is a useful scaffold, but its current report is a warning against making a generalization claim: it says synthetic data only, evaluates a seeded 300,000-row sample of 874,498, and holds out 39 of 127 merchants. The hybrid gets unseen-merchant macro F1 0.529; `GAS` has no unseen support, `HOME_IMPROVEMENT` F1 is 0, and fuel/automotive recall is 0.135/0.196. Rule coverage is 15.3% on unseen merchants (with 100% accuracy on those rule hits), while model accuracy on non-rule rows is 48.2%. These are generator-specific diagnostics, not real-market estimates. [Report scope/split](../../reports/TRANSACTION_CATEGORISATION.md#L1-L22) · [per-category results](../../reports/TRANSACTION_CATEGORISATION.md#L24-L35) · [rule coverage/accuracy](../../reports/TRANSACTION_CATEGORISATION.md#L52-L73)

1. **Establish a genuine gold audit set and baseline first (small-to-medium; annotation/data-owner dependency).** Preserve the existing merchant split but report category support and repeat over several seeds; collect a small reviewed set from actual, de-identified transaction descriptions if permitted. Split by merchant before fitting any rules/label models; keep the reviewed test labels out of LFs, feature generation, and model training. The current evaluator already records fit rows and merchant-group splits, but the committed tests use a hand-built synthetic merchant catalogue and check split consistency, not real-data quality. [Split implementation](../../src/greenpath/evaluation/transaction.py#L83-L115) · [synthetic test fixture](../../tests/ml/test_transaction_classifier.py#L28-L67) · [holdout tests](../../tests/ml/test_transaction_classifier.py#L232-L279)
2. **Implement explicit LFs and label aggregation (medium; label/data expertise; optional library review).** Add a separate `transaction_weak_supervision` module, leaving current rules as a baseline. Have each LF emit class evidence or `ABSTAIN`, and record coverage, overlaps, conflicts, and estimated accuracy. Candidate sources are high-precision text patterns and, only with appropriate history/grouping, recurring amount/date patterns. Fit a probabilistic label model on training data only; inspect the chosen library’s current treatment of correlated LFs and abstentions because the paper itself reports a Naive-Bayes/abstention limitation in the Snorkel implementation it used. Test that all-abstain and conflicting rows are not silently converted to `OTHER` or gold negatives. [Candidate paper LF sources](../../research-papers/weakly-supervised-bank-transaction-classification.md#L285-L349) · [raw transaction fields](../../src/greenpath/pipelines/schemas.py#L72-L93) · [current dependencies](../../pyproject.toml#L10-L27)
3. **Train/evaluate a discriminative model from weak labels (large for the paper-faithful sequence model; package and resource dependency).** First compare the current text model trained from label-model outputs with the label-model predictions and current supervised hybrid on the same merchant-heldout gold set. A faithful follow-on adds transaction-corpus embeddings and grouped amount/date sequence modeling; it requires a training/data path that accepts histories, not just `descriptions, categories`. PyTorch, Snorkel, and FastText tooling are not in the current declared dependencies, so approve dependency, privacy, runtime, and inference-budget impact before selecting that path. [Current fit API](../../src/greenpath/models/transaction_classifier.py#L329-L347) · [paper architecture](../../research-papers/weakly-supervised-bank-transaction-classification.md#L350-L389) · [declared dependencies](../../pyproject.toml#L10-L27)
4. **Acceptance / go-no-go.** Unit-test LF abstention, conflict handling, reproducibility, and train/test merchant isolation; assert truth/test labels never enter LF fitting or model features. On an untouched, merchant-disjoint reviewed set, report LF coverage/overlap/conflict and heldout label quality; compare label-model and downstream model balanced accuracy for one-vs-rest tasks, plus macro/per-class F1 for the multiclass baseline. If confidence gates or abstention are added, report coverage-risk curves and Brier/ECE; do not label raw maximum probabilities “calibrated.” Proposed initial performance gate: ≥0.03 absolute macro-F1 gain over the frozen hybrid baseline with bootstrap lower confidence bound above zero, and no supported category falling more than 0.05; choose this before seeing test results. If no real reviewed holdout is available, limit the submission claim to synthetic-generator performance.

**Submission payoff:** this would make a defensible “learn from unlabeled transaction volume with a small audit set” contribution rather than describing ordinary supervised training plus routing rules as weak supervision. It could reduce annotation burden and improve new-merchant coverage, but only if the generated labels and downstream classifier beat the current baseline on independently reviewed unseen merchants. Existing results indicate a substantial gap to close; the paper’s reported average balanced accuracy uses different binary tasks/data and is not evidence of GreenPath performance. [Paper’s task/result scope](../../research-papers/weakly-supervised-bank-transaction-classification.md#L560-L621) · [GreenPath unseen results](../../reports/TRANSACTION_CATEGORISATION.md#L24-L35)

## 3. Cross-paper recommendation, dependencies, and unresolved questions

### Recommended priority

1. **Do not claim either paper’s named method is already implemented.** Current evidence supports “flat supervised text categorisation with rule-first routing, plus synthetic merchant-heldout evaluation”; it does not support “hierarchical classification” or “weak supervision.” [Classifier overview](../../src/greenpath/models/transaction_classifier.py#L1-L40) · [evaluation caveat](../../reports/TRANSACTION_CATEGORISATION.md#L1-L5)
2. **Do evaluation/data readiness before architecture investment.** The existing merchant split is a strong start, but the committed results are synthetic, one heldout category has no merchants, and some unseen F1s are poor. Obtain a reviewed, merchant-disjoint set and report uncertainty/coverage before spending on either model. The current report has high known-merchant scores but much lower unseen scores, so random-row validation alone would be misleading for the intended unseen-brand use case. [Split and support](../../reports/TRANSACTION_CATEGORISATION.md#L17-L35) · [evaluation protocol](../../src/greenpath/evaluation/transaction.py#L1-L15)
3. **Choose the paper by the product gap.** If category-parent consistency and rollups are the objective, define a business-owned taxonomy first and prototype hierarchy constraints. If label scarcity is the objective, start with LFs + probabilistic label modeling and an independent gold audit set. These are complementary research directions, not interchangeable features: a flat classifier with rules is not a weak label model, and a set of flat labels is not a taxonomy.
